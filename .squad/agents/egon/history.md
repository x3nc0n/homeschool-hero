- 2026-07-22T18:07:07-05:00 — **Security Amendment: Issue #411 — Five Design Gaps Resolved.** Winston's pre-implementation review caught five gaps in the original API token design. Rulings: (1) `token_type=api_token` with missing/unregistered/revoked `jti` → hard 401; external JWTs skip `api_tokens` lookup entirely — branching on `token_type` claim is the discriminator. (2) All three `/api/auth/api-tokens` endpoints require `manage_security` + family-scoped queries; cross-family → 404 not 403. (3) `manage_grading` IS delegatable; grading router must migrate from `require_teacher()` to `require_capabilities(Capability.manage_grading)` for API token compat. (4) Max-token enforcement: count-then-insert (no `SELECT FOR UPDATE`) + `UNIQUE(family_id, name)` DB constraint; soft cap acceptable for self-hosted single-family app. (5) Capability intersection pinned at `_resolve_bearer_session_claims` via new `BearerSessionClaims.token_capabilities` field; `AuthSession.__post_init__` already respects pre-populated caps. **Durable lessons:** (a) Always branch credential-type checks explicitly on a `token_type` claim rather than inferring from table lookup presence/absence. (b) SQLite compatibility means no row-level locking — use unique constraints for correctness, application-level counts for UX. (c) `manage_security` must NEVER be delegatable to tokens — it's the mint authority itself. (d) Pre-implementation security review catches design ambiguities cheaply; make it standard for auth features.
